# אפיון: מסך "הרשאות מערכות" (ריכוז הרשאות עובדים למערכות הארגון)

סטטוס: טיוטה לאישור · אין עדיין קוד, רק אפיון.

## 1. המטרה

מסך נפרד מ"משאבים" שמרכז את כל ההרשאות שעובדים מקבלים למערכות הארגון
(פריוריטי, ויפלנס, סמנטו, מסימון, תפעול 360, כוננים), ומחזיק עבור כל הרשאה
תיעוד מלא לצורכי אבטחת מידע:

- מי ביקש, מתי, ובאיזו חתימה.
- מי אישר ומי ביצע, ומתי.
- מאיזה יום ושעה ההרשאה בתוקף (ברירת מחדל: יום תחילת העבודה, 08:00).
- מתי נסגרה (בסיום העסקה או בביטול).

היום הרשאות דיגיטליות נשמרות כפריטים בדומיין `digital` של המשאבים, ונכנסות
לקליטה כ־`onboarding_items` מסוג `access` (`NewOnboardingDialog.tsx`). אין שם מושג של
"סביבה", אין תאריך תחילת תוקף ואין מחזור חיים של הרשאה, ולכן זה לא עובד טוב.

## 2. מושגים

| מושג | הסבר | דוגמה |
|---|---|---|
| מערכת | תוכנה שאפשר לתת אליה הרשאה | פריוריטי |
| סביבה | חלק בתוך המערכת שההרשאה ניתנת אליו. נוספת בשדה חופשי | כספים, הנדסה, רכש, התחדשות עירונית |
| שיטת פתיחה | איך ההרשאה נפתחת בפועל | אוטומטית / ידנית / קריאה לאיש IT |
| הרשאה | שורה אחת: עובד × מערכת × סביבה, עם מחזור חיים | משה כהן · פריוריטי · כספים |

### שיטות פתיחה

לכל מערכת נפתחת **קריאת שירות ופרוטוקול נפרדים** (סעיף 3). שיטת הפתיחה קובעת מה
קורה בתוך הקריאה של אותה מערכת:

| מערכת | שיטה | מה קורה בקריאה שלה |
|---|---|---|
| תפעול 360 | `auto_tiful360` | כפתור "בצע": נפתח משתמש אוטומטית דרך `manage-users` (פעולת `invite` הקיימת) |
| מסימון | `auto_mesimon` | כפתור "בצע": נפתח משתמש אוטומטית דרך פונקציה חדשה ב-API של מסימון (ראו שאלות פתוחות) |
| פריוריטי, ויפלנס, סמנטו | `manual` | המבצע פותח במערכת עצמה ומסמן "בוצע" עם תאריך, שעה ושם משתמש |
| כוננים | `it` | הקריאה מוקצית לאיש ה-IT. הוא מקבל התראה, רואה את הפרוטוקול ומסמן "בוצע" לכל כונן |

השיטה והמבצע הם שדות בהגדרות המערכת, ולא קוד קשיח, כך שאפשר להוסיף מערכות בלי פיתוח.

## 3. העיקרון: קריאה ופרוטוקול נפרדים לכל מערכת

ברגע שמשאבי אנוש מגדירה שצריך לפתוח לעובד הרשאות, נפתחת **קריאת שירות נפרדת לכל
מערכת**, כולל כוננים, ולכל קריאה **פרוטוקול בקשה משלה**. עובד שמקבל פריוריטי,
ויפלנס וכוננים מקבל שלוש קריאות:

- "פתיחת הרשאות פריוריטי – משה כהן"
- "פתיחת הרשאות ויפלנס – משה כהן"
- "פתיחת הרשאות כוננים – משה כהן"

בתוך כל קריאה, הסביבות של אותה מערכת הן השורות לביצוע. אותו דבר בניתוק: קריאת
"ניתוק הרשאות <מערכת> – משה כהן" לכל מערכת שיש לעובד בה הרשאה פעילה.

```
HR מגדירה וחותמת פעם אחת
        │
        ├──▶ קריאה + פרוטוקול: פריוריטי (כספים, רכש)   ──▶ מבצע: אדמין
        ├──▶ קריאה + פרוטוקול: ויפלנס (הנדסה)          ──▶ מבצע: אדמין
        ├──▶ קריאה + פרוטוקול: תפעול 360               ──▶ "בצע" אוטומטי
        └──▶ קריאה + פרוטוקול: כוננים (S:, P:)          ──▶ מבצע: איש IT
                                                          │
                     כל קריאה נסגרת לבד כשכל הסביבות שלה טופלו,
                     ומפיקה פרוטוקול ביצוע (V2) משלה
```

כך כל מבצע רואה רק את המערכת שלו (איש ה-IT רואה רק כוננים), וכל פרוטוקול הוא מסמך
עצמאי למבקר. החתימה של משאבי אנוש נעשית פעם אחת ומוטבעת בכל הפרוטוקולים של
אותה הגשה.

## 4. מחזור חיים

### הרשאה בודדת (שורה בתוך הקריאה)

```
ממתין לביצוע ──ביצוע──▶ פעיל ──בקשת ניתוק──▶ ממתין לניתוק ──ביצוע──▶ סגור
     │
     └──דחייה──▶ נדחה (עם סיבה)
```

- `pending`: נוצרה מבקשת משאבי אנוש ויושבת בקריאת הפתיחה.
- `active`: נפתחה בפועל. במערכות האוטומטיות זה קורה בלחיצה על "בצע" בתוך הקריאה.
- `revoke_pending` → `revoked`: יושבת בקריאת הניתוק עד שמבצעים.
- `rejected`: לא תיפתח, עם סיבה שמופיעה בפרוטוקול.

כל מעבר נרשם עם המשתמש המחובר ועם צילום של שם התצוגה שלו, כמו בתהליך הניתוק
(כלל ב-`AGENTS.md`).

### הבקשה (קריאה אחת למערכת אחת)

`open` כל עוד יש בה סביבה שלא טופלה, ו-`done` כשכל הסביבות שלה פעילות/נותקו/נדחו.
הסגירה נעשית אוטומטית, בעדכון מותנה, כדי שלא תדרוס סגירה ידנית במקביל (כמו
`ticket-handling-status`).

### שני תאריכים, לא אחד

לצורכי ביקורת חשוב להפריד בין:

- **תוקף מבוקש** (`effective_from`): ברירת מחדל `start_date` של העובד בשעה 08:00
  (שעון ישראל), וניתן לשינוי בטופס. ממנו "המונה מתחיל לרוץ".
- **ביצוע בפועל** (`executed_at`): מתי ההרשאה נפתחה באמת.

אם הביצוע מגיע אחרי יום תחילת העבודה, הפרוטוקול יציג את שניהם. אחרת מבקר יראה
הרשאה "מיום 1" שבפועל נפתחה רק אחרי שבוע. בניתוק זה אותו דבר: מועד ניתוק מבוקש
(ברירת מחדל: יום העבודה האחרון בסוף היום) מול מועד ניתוק בפועל.

## 5. מבנה נתונים (Supabase)

כל הטבלאות company-scoped, עם RLS לפי `user_company_ids` והתפקידים הקיימים.

```sql
-- מערכות
create table org_systems (
  id uuid primary key default gen_random_uuid(),
  company_id uuid not null references companies(id) on delete cascade,
  name text not null,                       -- פריוריטי
  provisioning text not null default 'manual'
    check (provisioning in ('auto_tiful360','auto_mesimon','manual','it')),
  executor_role text not null default 'admin',  -- מי מבצע את השורה בקריאה (כוננים: it_manager)
  is_active boolean not null default true,
  sort_order int not null default 0
);

-- סביבות (שדה חופשי לכל מערכת)
create table org_system_environments (
  id uuid primary key default gen_random_uuid(),
  system_id uuid not null references org_systems(id) on delete cascade,
  company_id uuid not null,                 -- נקבע ב-trigger מהמערכת, לא מהלקוח
  name text not null,                       -- כספים / הנדסה / רכש ...
  is_active boolean not null default true
);

-- בקשה = קריאת שירות אחת + פרוטוקול אחד, למערכת אחת (פתיחה או ניתוק)
create table access_requests (
  id uuid primary key default gen_random_uuid(),
  company_id uuid not null references companies(id),
  employee_id uuid not null references employees(id),
  system_id uuid not null references org_systems(id),
  submission_id uuid not null,              -- מקשר את כל הקריאות של אותה הגשה של HR
  kind text not null check (kind in ('grant','revoke')),
  status text not null default 'open' check (status in ('open','done')),
  it_ticket_id uuid not null references it_tickets(id),
  requested_by uuid not null, requested_by_name text not null,
  requested_at timestamptz not null default now(),
  request_signature text,                   -- חתימת המבקש/ת (SignaturePad)
  request_protocol_path text,               -- PDF פרוטוקול בקשה (V1)
  execution_protocol_path text,             -- PDF פרוטוקול ביצוע (V2), בסגירה
  onboarding_process_id uuid references onboarding_processes(id),
  offboarding_process_id uuid
);

-- הרשאות (שורה לכל עובד × מערכת × סביבה)
create table access_grants (
  id uuid primary key default gen_random_uuid(),
  company_id uuid not null references companies(id),
  employee_id uuid not null references employees(id),
  system_id uuid not null references org_systems(id),
  environment_id uuid references org_system_environments(id),  -- null = כל המערכת
  status text not null default 'pending',
  effective_from timestamptz not null,      -- ברירת מחדל: start_date 08:00 Asia/Jerusalem
  effective_to timestamptz,                 -- מועד ניתוק מבוקש
  grant_request_id uuid not null references access_requests(id),
  revoke_request_id uuid references access_requests(id),
  executed_by uuid, executed_by_name text, executed_at timestamptz,
  revoked_by uuid, revoked_by_name text, revoked_at timestamptz,
  external_username text,                   -- שם המשתמש שנפתח במערכת החיצונית
  notes text,
  rejection_reason text
);

-- לא יותר מהרשאה פתוחה אחת לאותו עובד × מערכת × סביבה
create unique index access_grants_one_open
  on access_grants (employee_id, system_id, coalesce(environment_id, '00000000-0000-0000-0000-000000000000'))
  where status not in ('revoked','rejected');

-- לא יותר מבקשה פתוחה אחת מאותו סוג לאותו עובד × מערכת
create unique index access_requests_one_open
  on access_requests (employee_id, system_id, kind) where status = 'open';
```

**יומן ביקורת:** כל שינוי ב-`access_grants` וב-`access_requests` נרשם ביומן
append-only. ההמלצה היא להרחיב את `permission_audit_log` הקיים עם triggers על
הטבלאות, כי זה בדיוק התפקיד שלו ("מי שינה איזו גישה"). שורות לא נמחקות. ביטול הוא
מעבר סטטוס.

**כתיבה אטומית:** פונקציית DB אחת (`request_access`) יוצרת בטרנזקציה אחת, לכל
מערכת שסומנה, בקשה, קריאת שירות ושורות סביבה. או שכל הקריאות של ההגשה נפתחות, או
אף אחת, כך שלא תיתכן קריאה בלי שורות או הגשה שנפתחה חלקית.
גם ביצוע שורה (`complete_access_grant`) וסגירת הבקשה עוברים בפונקציות שבודקות tenant
ותפקיד. זה אותו דפוס שבו מתחיל הניתוק.

## 6. קריאת ההרשאה של מערכת: מה רואים כשנכנסים אליה

קריאה ב-`it_tickets` מסוג חדש `access`, עם הנושא "פתיחת הרשאות <מערכת>" או "ניתוק
הרשאות <מערכת>". היא מוקצית לתפקיד המבצע של המערכת (`executor_role`), כך שכוננים
מגיעים לאיש ה-IT ושאר המערכות לאדמין. היא מופיעה ברשימת הקריאות הרגילה
(`/it-tickets`), ו-`notify-it-ticket` שולח מייל למבצע כרגיל. בכניסה לקריאה, מעל
השיחה הרגילה, מופיע פאנל:

**1. פרוטוקול הבקשה של המערכת הזאת בלבד:** כפתור לפתיחת ה-PDF החתום. בו פרטי העובד,
תאריך תחילת עבודה, שם המערכת, הסביבות עם מועד התוקף המבוקש, ובסוף שם המבקש/ת,
תאריך ושעה וחתימה. מזהה מסמך לכל מערכת, למשל `ACC-PRI-XXXXXXXX-V1`.

**2. רשימת ביצוע**, שורה לכל סביבה. דוגמה לקריאת פריוריטי:

| סביבה | בתוקף מ | סטטוס | פעולה |
|---|---|---|---|
| כספים | 02/11/2026 08:00 | ✓ בוצע 01/11 14:20 · moshe.c | — |
| רכש | 02/11/2026 08:00 | ממתין | **סמן כבוצע** / דחה |

- "סמן כבוצע" פותח דיאלוג קטן: תאריך ושעת ביצוע (ברירת מחדל: עכשיו) ושם משתמש
  במערכת החיצונית. אפשר לסמן את כל הסביבות בבת אחת.
- בקריאה של **תפעול 360** או **מסימון** יש כפתור "בצע" שפותח את המשתמש אוטומטית.
- בקריאת **כוננים** השורות הן הכוננים (S:, P:...), ורק איש ה-IT רואה ומבצע אותה.
- בקריאת **ניתוק** הרשימה זהה, עם "נותק" במקום "בוצע". בתפעול 360 "בצע" חוסם את
  המשתמש, ובמסימון מבטלים משתמש אם ה-API מאפשר זאת.

**3. סגירה:** כשהסביבה האחרונה מטופלת, הקריאה נסגרת אוטומטית ומפיקה פרוטוקול ביצוע
(V2) של אותה מערכת: מי ביצע כל סביבה ומתי. הוא נשמר בתיק העובד, כמו בקליטה
(`useOnboardingProtocol` מפיק V1 בשליחה ו-V2 אחרי ביצוע).

> קריאות לא נשלחות למסימון אלא דרך `create-mesimon-task` ורק לחברות ב-`MESIMON_COMPANY_IDS`
> (כלל קיים). אם רוצים, אפשר לשלוח קריאת הרשאה כמשימה למסימון בכפתור הקיים, אבל
> הסטטוס של כל סביבה מנוהל בתפעול 360.

## 7. המסך החדש: `/system-access` ("הרשאות מערכות")

נתיב חדש ב-`App.tsx` ופריט בתפריט. גישה: `admin`, `super_admin`, `it_manager`, `hr`
ו-`operations`. הביצוע עצמו קורה בתוך הקריאה. המסך הוא מקום הריכוז, המעקב
והפרוטוקולים.

### לשונית 1: "קריאות פתוחות"

רשימת קריאות ההרשאה הפתוחות (פתיחה וניתוק), מקובצת לפי עובד והגשה, כדי לראות את
כל המערכות של אותו עובד יחד:

| עובד | מערכת | סוג | סביבות שבוצעו | מבצע | ותק הקריאה |
|---|---|---|---|---|---|
| משה כהן | פריוריטי | פתיחה | 1/2 | אדמין | יומיים |
| משה כהן | כוננים | פתיחה | 0/2 | איש IT | יומיים |

לחיצה פותחת את הקריאה של אותה מערכת.

### לשונית 2: "מטריצה"

שורות לפי עובדים, עמודות לפי מערכות, ובתא הסביבות הפעילות. סינון לפי מחלקה,
מערכת וסטטוס. זו "תמונת המצב" לביקורת: מי נגיש למה, עכשיו. טבלה סמנטית עם
כותרות עמודה ופקדים מזוהים (כלל הנגישות של רשימות הנכסים).

### לשונית 3: "לפי עובד" + הפקת פרוטוקול

בוחרים עובד ומקבלים ציר זמן של כל ההרשאות שלו, כולל סגורות, וקישורים לכל
הקריאות שלו. "הפק פרוטוקול הרשאות" (PDF):

- כותרת עם לוגו החברה, פרטי עובד, תאריך תחילת עבודה ומזהה מסמך
  (`ACC-XXXXXXXX-V1`, כמו `onboardingDocumentId`).
- טבלה: מערכת · סביבה · בתוקף מ (תאריך ושעה) · בוצע בפועל · בוצע ע"י · נותק ב.
- בסוף: מי ביקש וחתימה, מספר הקריאה של כל מערכת ותאריך הפקה.

זה דוח מרכז לכל המערכות. הפרוטוקולים לכל מערכת נשארים מסמכים נפרדים, ויש אליהם
קישורים מכל שורה.
- המסמך נשמר בתיק העובד (`employee_documents`), כמו פרוטוקול הקליטה.

אפשר להפיק גם "כל ההרשאות למערכת X", למשל כל מי שנגיש לפריוריטי־כספים.

### לשונית 4: "מערכות וסביבות" (הגדרות)

ניהול רשימת המערכות: שם, שיטת פתיחה ומבצע. מתחת לכל מערכת, סביבות בשדות
חופשיים: הוספה, שינוי שם והשבתה. אין מחיקה של סביבה שיש לה הרשאות. רק משביתים.

### בקשה יזומה (לא דרך קליטה)

כפתור "בקשת הרשאה" / "בקשת ניתוק" לעובד קיים, למשל כשעובד עובר מחלקה: אותו
טופס בחירת מערכות וסביבות, אותה חתימה, ונפתחת קריאה עם פרוטוקול לכל מערכת שנבחרה.

## 8. החיבור לטופס קליטת עובד

בתוך `NewOnboardingDialog` מתווסף שלב/מקטע **"הרשאות למערכות"**, נפרד מהמשאבים:

1. רשימת מערכות עם תיבות סימון.
2. סימון מערכת פותח בחירת סביבות (בחירה מרובה, עם אפשרות "+ סביבה חדשה" למי
   שמורשה).
3. שדה "בתוקף מ" מתמלא ב-`start_date` 08:00 וניתן לשינוי לכל מערכת.
4. "העתק מעובד קיים" מעתיק גם הרשאות (כמו `copyFromEmployee` הקיים לנכסים).
5. ב"שליחה לתפעול" (`SendToOpsDialog`) משאבי אנוש חותמת (`SignaturePad`), ו-
   `request_access` פותחת קריאה ופרוטוקול בקשה לכל מערכת שסומנה. הקריאות האלה
   נפרדות מקריאת הקליטה של הציוד, כי מבצעים אחרים מטפלים בהן.

## 9. סיום העסקה

כשמתחיל תהליך ניתוק (הפונקציה האטומית הקיימת), נפתחת אוטומטית **קריאת "ניתוק
הרשאות" ופרוטוקול ניתוק לכל מערכת** שיש לעובד בה הרשאה פעילה, כולל כוננים לאיש ה-IT. מועד הניתוק המבוקש הוא יום
העבודה האחרון, וניתן לשינוי. ביצוע כל שורה ממלא `revoked_at`, וכך הפרוטוקול מציג
תקופה מלאה "מ… עד…" לכל הרשאה. פרוטוקולי הניתוק נשמרים בתיק העובד לצד טופס הניתוק.

## 10. מיגרציה מהמצב הקיים

סקריפט חד-פעמי שממיר את הפריטים בדומיין `digital` שמשויכים לעובדים לשורות
`access_grants` בסטטוס `active`. `effective_from` נלקח מתאריך השיוך, ואם אין, מ-
`start_date` 08:00, עם הערה "יובא מהמשאבים". אחרי האימות מסתירים את ההרשאות ממסך
המשאבים.

## 11. שלבי ביצוע מוצעים

1. טבלאות, RLS, פונקציות DB, יומן ביקורת ולשונית "מערכות וסביבות".
2. `request_access`: קריאה מסוג `access` ופרוטוקול בקשה לכל מערכת, ופאנל הביצוע בתוך הקריאה.
3. מסך `/system-access`: קריאות פתוחות, מטריצה, לפי עובד ופרוטוקולים.
4. חיבור לטופס הקליטה וחתימת משאבי אנוש.
5. אוטומציות: תפעול 360 (`manage-users`), מסימון (אחרי אימות API).
6. קריאת ניתוק מתוך תהליך הניתוק, ומיגרציה מהמשאבים.

## 12. שאלות פתוחות

1. **מסימון:** ל-`create-mesimon-task` יש היום רק יצירת משימות ושליפת משתמשים. צריך
   לאמת שב-API של מסימון יש endpoint ליצירת משתמש, ומה הוא מקבל (מייל, הרשאות,
   סביבה?).
2. **מי מבצע בקריאה?** אדמין בלבד, או גם `it_manager` לכל השורות? האם המבקש/ת
   יכול/ה לסמן ביצוע בעצמו/ה? ההמלצה: לא, הפרדת סמכויות.
3. **סביבות בתפעול 360:** האם "סביבה" כאן היא תפקיד (`user_roles`)? אם כן, אישור
   יכול לתת גם את התפקיד, דרך `set-role` הקיים, שכבר כותב ל-`permission_audit_log`.
4. **כוננים:** האם הסביבות הן אותיות כוננים / תיקיות, ונדרשת גם רמת הרשאה
   (קריאה / כתיבה)? אם כן, מוסיפים שדה "רמה" להרשאה.
5. **שעת ברירת מחדל 08:00:** קבועה לכל החברות, או הגדרה ברמת חברה?
