# אפיון: מסך "הרשאות מערכות" (ריכוז הרשאות עובדים למערכות הארגון)

סטטוס: טיוטה לאישור · אין עדיין קוד, רק אפיון.

## 1. המטרה

מסך נפרד מ"משאבים" שמרכז את כל ההרשאות שעובדים מקבלים למערכות הארגון
(פריוריטי, ויפלנס, סמנטו, מסימון, תפעול 360, כוננים), ומחזיק עבור כל הרשאה
תיעוד מלא לצורכי אבטחת מידע:

- מי ביקש, מתי, ובאיזו חתימה.
- מי אישר ומי ביצע, ומתי.
- מאיזה יום ושעה ההרשאה בתוקף (ברירת מחדל: יום תחילת העבודה, 08:00).
- מתי נסגרה (בסיום העסקה או בביטול).

היום הרשאות דיגיטליות נשמרות כפריטים בדומיין `digital` של המשאבים, ונכנסות
לקליטה כ־`onboarding_items` מסוג `access` (`NewOnboardingDialog.tsx`). אין שם מושג של
"סביבה", אין תאריך תחילת תוקף ואין מחזור חיים של הרשאה, ולכן זה לא עובד טוב.

## 2. מושגים

| מושג | הסבר | דוגמה |
|---|---|---|
| מערכת | תוכנה שאפשר לתת אליה הרשאה | פריוריטי |
| סביבה | חלק בתוך המערכת שההרשאה ניתנת אליו. נוספת בשדה חופשי | כספים, הנדסה, רכש, התחדשות עירונית |
| שיטת פתיחה | איך ההרשאה נפתחת בפועל | אוטומטית / ידנית |
| אחראי | מי מבצע את הפתיחה והניתוק במערכת. קובע לאיזו קריאה היא נכנסת | אדמין, איש IT |
| הרשאה | שורה אחת: עובד × מערכת × סביבה, עם מחזור חיים | משה כהן · פריוריטי · כספים |

### שיטות פתיחה

לכל מערכת מוגדרים **שיטת פתיחה** ו**אחראי**. האחראי קובע לאיזו קריאה המערכת
נכנסת (סעיף 3), והשיטה קובעת מה עושים בשורה שלה בתוך הקריאה:

| מערכת | שיטה | אחראי (דוגמה) | מה עושים בשורה |
|---|---|---|---|
| תפעול 360 | `auto_tiful360` | אדמין | כפתור "בצע": נפתח משתמש אוטומטית דרך `manage-users` (פעולת `invite` הקיימת) |
| מסימון | `auto_mesimon` | אדמין | כפתור "בצע": נפתח משתמש אוטומטית דרך פונקציה חדשה ב-API של מסימון (ראו שאלות פתוחות) |
| פריוריטי, ויפלנס, סמנטו | `manual` | אדמין | פותחים במערכת עצמה ומסמנים "בוצע" עם תאריך, שעה ושם משתמש |
| כוננים | `manual` | איש IT | איש ה-IT פותח ומסמן "בוצע" לכל כונן |

השיטה והאחראי הם שדות בהגדרות המערכת, ולא קוד קשיח, כך שאפשר להוסיף מערכות או
להעביר מערכת לאחראי אחר בלי פיתוח.

## 3. העיקרון: קריאה לכל אחראי, פרוטוקול אחד לעובד

כשמשאבי אנוש מגישה בקשה (חתימה אחת), המערכת **מפיקה יחד את כל הקריאות, קריאה
נפרדת לכל אחראי**. כל קריאה מכילה את כל המערכות והסביבות שבאחריות אותו אחראי.
לצד זה נוצר **פרוטוקול אחיד אחד לעובד**, שמרכז את כל המערכות.

דוגמה: משה כהן מקבל פריוריטי, ויפלנס, תפעול 360 וכוננים.

```
HR מגדירה וחותמת פעם אחת
        │
        ├──▶ קריאה לאדמין:   "פתיחת הרשאות – משה כהן"
        │                    פריוריטי (כספים, רכש) · ויפלנס (הנדסה) · תפעול 360
        │
        ├──▶ קריאה לאיש IT:  "פתיחת הרשאות – משה כהן"
        │                    כוננים (S:, P:)
        │
        └──▶ פרוטוקול בקשה אחיד: משה כהן · כל המערכות, ממוין לפי מערכת
```

- כל קריאה נסגרת לבד כשכל השורות שבה טופלו.
- כשכל הקריאות של ההגשה נסגרו, נוצר **פרוטוקול ביצוע אחיד (V2)** לעובד, עם מי ביצע
  כל שורה ומתי. הוא נשמר בתיק העובד.
- אותו דבר בניתוק: קריאת "ניתוק הרשאות" לכל אחראי, ופרוטוקול ניתוק אחיד לעובד.

## 4. מחזור חיים

### הרשאה בודדת (שורה בתוך קריאה)

```
ממתין לביצוע ──ביצוע──▶ פעיל ──בקשת ניתוק──▶ ממתין לניתוק ──ביצוע──▶ סגור
     │
     └──דחייה──▶ נדחה (עם סיבה)
```

- `pending`: נוצרה מבקשת משאבי אנוש ויושבת בקריאה של האחראי.
- `active`: נפתחה בפועל. במערכות האוטומטיות זה קורה בלחיצה על "בצע" בתוך הקריאה.
- `revoke_pending` → `revoked`: יושבת בקריאת הניתוק של האחראי עד שמבצעים.
- `rejected`: לא תיפתח, עם סיבה שמופיעה בפרוטוקול.

כל מעבר נרשם עם המשתמש המחובר ועם צילום של שם התצוגה שלו, כמו בתהליך הניתוק
(כלל ב-`AGENTS.md`).

### קריאה (לאחראי) והגשה (לעובד)

- קריאה: `open` כל עוד יש בה שורה שלא טופלה, ו-`done` כשכל השורות שלה טופלו.
- הגשה: `open` כל עוד אחת הקריאות שלה פתוחה, ו-`done` כשכולן נסגרו. אז מופק
  פרוטוקול הביצוע האחיד.

הסגירות נעשות אוטומטית, בעדכון מותנה, כדי שלא ידרסו סגירה ידנית במקביל (כמו
`ticket-handling-status`).

### שני תאריכים, לא אחד

לצורכי ביקורת חשוב להפריד בין:

- **תוקף מבוקש** (`effective_from`): ברירת מחדל `start_date` של העובד בשעה 08:00
  (שעון ישראל), וניתן לשינוי בטופס. ממנו "המונה מתחיל לרוץ".
- **ביצוע בפועל** (`executed_at`): מתי ההרשאה נפתחה באמת.

אם הביצוע מגיע אחרי יום תחילת העבודה, הפרוטוקול יציג את שניהם. אחרת מבקר יראה
הרשאה "מיום 1" שבפועל נפתחה רק אחרי שבוע. בניתוק זה אותו דבר: מועד ניתוק מבוקש
(ברירת מחדל: יום העבודה האחרון בסוף היום) מול מועד ניתוק בפועל.

## 5. מבנה נתונים (Supabase)

כל הטבלאות company-scoped, עם RLS לפי `user_company_ids` והתפקידים הקיימים.

```sql
-- מערכות
create table org_systems (
  id uuid primary key default gen_random_uuid(),
  company_id uuid not null references companies(id) on delete cascade,
  name text not null,                       -- פריוריטי
  provisioning text not null default 'manual'
    check (provisioning in ('auto_tiful360','auto_mesimon','manual')),
  owner_role text not null default 'admin', -- האחראי: תפקיד (כוננים: it_manager)
  owner_user_id uuid,                       -- או אחראי מסוים; גובר על התפקיד
  is_active boolean not null default true,
  sort_order int not null default 0         -- סדר המערכות בפרוטוקול ובמסך
);

-- סביבות (שדה חופשי לכל מערכת)
create table org_system_environments (
  id uuid primary key default gen_random_uuid(),
  system_id uuid not null references org_systems(id) on delete cascade,
  company_id uuid not null,                 -- נקבע ב-trigger מהמערכת, לא מהלקוח
  name text not null,                       -- כספים / הנדסה / רכש ...
  is_active boolean not null default true
);

-- הגשה = בקשה אחת של HR לעובד אחד, עם פרוטוקול אחיד אחד
create table access_submissions (
  id uuid primary key default gen_random_uuid(),
  company_id uuid not null references companies(id),
  employee_id uuid not null references employees(id),
  kind text not null check (kind in ('grant','revoke')),
  status text not null default 'open' check (status in ('open','done')),
  requested_by uuid not null, requested_by_name text not null,
  requested_at timestamptz not null default now(),
  request_signature text,                   -- חתימת המבקש/ת (SignaturePad)
  request_protocol_path text,               -- PDF פרוטוקול בקשה אחיד (V1)
  execution_protocol_path text,             -- PDF פרוטוקול ביצוע אחיד (V2)
  onboarding_process_id uuid references onboarding_processes(id),
  offboarding_process_id uuid
);

-- קריאה = אחראי אחד בתוך הגשה אחת
create table access_tickets (
  id uuid primary key default gen_random_uuid(),
  submission_id uuid not null references access_submissions(id),
  company_id uuid not null,                 -- נקבע ב-trigger מההגשה
  owner_role text not null,
  owner_user_id uuid,
  it_ticket_id uuid not null references it_tickets(id),
  status text not null default 'open' check (status in ('open','done'))
);

-- הרשאות (שורה לכל עובד × מערכת × סביבה)
create table access_grants (
  id uuid primary key default gen_random_uuid(),
  company_id uuid not null references companies(id),
  employee_id uuid not null references employees(id),
  system_id uuid not null references org_systems(id),
  environment_id uuid references org_system_environments(id),  -- null = כל המערכת
  status text not null default 'pending',
  effective_from timestamptz not null,      -- ברירת מחדל: start_date 08:00 Asia/Jerusalem
  effective_to timestamptz,                 -- מועד ניתוק מבוקש
  grant_ticket_id uuid not null references access_tickets(id),
  revoke_ticket_id uuid references access_tickets(id),
  executed_by uuid, executed_by_name text, executed_at timestamptz,
  revoked_by uuid, revoked_by_name text, revoked_at timestamptz,
  external_username text,                   -- שם המשתמש שנפתח במערכת החיצונית
  notes text,
  rejection_reason text
);

-- לא יותר מהרשאה פתוחה אחת לאותו עובד × מערכת × סביבה
create unique index access_grants_one_open
  on access_grants (employee_id, system_id, coalesce(environment_id, '00000000-0000-0000-0000-000000000000'))
  where status not in ('revoked','rejected');

-- קריאה אחת לכל אחראי בכל הגשה
create unique index access_tickets_one_per_owner
  on access_tickets (submission_id, owner_role, coalesce(owner_user_id, '00000000-0000-0000-0000-000000000000'));
```

**יומן ביקורת:** כל שינוי ב-`access_grants`, `access_tickets` ו-`access_submissions`
נרשם ביומן append-only. ההמלצה היא להרחיב את `permission_audit_log` הקיים עם
triggers על הטבלאות, כי זה בדיוק התפקיד שלו ("מי שינה איזו גישה"). שורות לא נמחקות.
ביטול הוא מעבר סטטוס.

**כתיבה אטומית:** פונקציית DB אחת (`request_access`) יוצרת בטרנזקציה אחת את ההגשה,
מקבצת את המערכות לפי אחראי, ופותחת קריאת שירות לכל אחראי עם השורות שלו. או שכל
הקריאות של ההגשה נפתחות, או אף אחת. גם ביצוע שורה (`complete_access_grant`)
והסגירות עוברים בפונקציות שבודקות tenant ותפקיד. זה אותו דפוס שבו מתחיל הניתוק.

## 6. הקריאה של האחראי: מה רואים כשנכנסים אליה

קריאה ב-`it_tickets` מסוג חדש `access`, עם הנושא "פתיחת הרשאות – <עובד>" או "ניתוק
הרשאות – <עובד>", מוקצית לאחראי. היא מופיעה ברשימת הקריאות הרגילה (`/it-tickets`),
ו-`notify-it-ticket` שולח מייל לאחראי כרגיל. בכניסה לקריאה, מעל השיחה הרגילה,
מופיע פאנל:

**1. הפרוטוקול האחיד של העובד:** כפתור לפתיחת ה-PDF החתום של ההגשה, עם כל המערכות.
השורות שבאחריות הקריאה הנוכחית מסומנות בו.

**2. רשימת ביצוע** של המערכות שבאחריות האחראי, **ממוינת ומקובצת לפי מערכת**.
דוגמה לקריאה של האדמין:

| מערכת | סביבה | בתוקף מ | סטטוס | פעולה |
|---|---|---|---|---|
| **פריוריטי** | כספים | 02/11/2026 08:00 | ✓ בוצע 01/11 14:20 · moshe.c | — |
| | רכש | 02/11/2026 08:00 | ממתין | **סמן כבוצע** / דחה |
| **ויפלנס** | הנדסה | 02/11/2026 08:00 | ממתין | **סמן כבוצע** / דחה |
| **תפעול 360** | — | 02/11/2026 08:00 | ממתין | **בצע** (פותח משתמש) |

- "סמן כבוצע" פותח דיאלוג קטן: תאריך ושעת ביצוע (ברירת מחדל: עכשיו) ושם משתמש
  במערכת החיצונית. אפשר לסמן מערכת שלמה, כל הסביבות שלה, בבת אחת.
- בקריאה של איש ה-IT מופיעים רק הכוננים.
- בקריאת **ניתוק** הרשימה זהה, עם "נותק" במקום "בוצע". בתפעול 360 "בצע" חוסם את
  המשתמש, ובמסימון מבטלים משתמש אם ה-API מאפשר זאת.

**3. סגירה:** כשהשורה האחרונה מטופלת, הקריאה נסגרת אוטומטית. כשהקריאה האחרונה של
ההגשה נסגרת, מופק פרוטוקול הביצוע האחיד (V2) ונשמר בתיק העובד, כמו בקליטה
(`useOnboardingProtocol` מפיק V1 בשליחה ו-V2 אחרי ביצוע).

> קריאות לא נשלחות למסימון אלא דרך `create-mesimon-task` ורק לחברות ב-`MESIMON_COMPANY_IDS`
> (כלל קיים). אם רוצים, אפשר לשלוח קריאת הרשאות כמשימה למסימון בכפתור הקיים, אבל
> הסטטוס של כל שורה מנוהל בתפעול 360.

## 7. הפרוטוקול האחיד לעובד

מסמך אחד לעובד, לכל המערכות, ממוין לפי מערכת (לפי `sort_order`) ובתוך מערכת לפי
סביבה:

- כותרת עם לוגו החברה, פרטי עובד, תאריך תחילת עבודה ומזהה מסמך
  (`ACC-XXXXXXXX-V1`, כמו `onboardingDocumentId`).
- טבלה: מערכת · סביבה · בתוקף מ (תאריך ושעה) · אחראי · בוצע בפועל · בוצע ע"י · נותק ב.
- בסוף: מי ביקש, תאריך, שעה וחתימה, ומספרי הקריאות של כל אחראי.
- שלוש גרסאות: בקשה (V1, בהגשה), ביצוע (V2, כשכל הקריאות נסגרו), וניתוק (בסיום
  העסקה). כולן נשמרות בתיק העובד (`employee_documents`).

בנוסף, אפשר להפיק בכל רגע ממסך ההרשאות **פרוטוקול מצב עדכני** לעובד: כל ההרשאות
שלו מאז ומעולם, ממוינות לפי מערכת.

## 8. המסך החדש: `/system-access` ("הרשאות מערכות")

נתיב חדש ב-`App.tsx` ופריט בתפריט. גישה: `admin`, `super_admin`, `it_manager`, `hr`
ו-`operations`. הביצוע עצמו קורה בתוך הקריאות. המסך הוא מקום הריכוז, המעקב
והפרוטוקולים. בכל הלשוניות יש **בורר תצוגה: לפי עובד / לפי מערכת**.

### לשונית 1: "קריאות פתוחות"

לפי עובד (ברירת מחדל):

| עובד | סוג | אחראי | מערכות | שורות שבוצעו | ותק |
|---|---|---|---|---|---|
| משה כהן | פתיחה | אדמין | פריוריטי, ויפלנס, תפעול 360 | 2/4 | יומיים |
| משה כהן | פתיחה | איש IT | כוננים | 0/2 | יומיים |

לפי מערכת: מה ממתין בכל מערכת, למשל "פריוריטי: 3 עובדים, 5 סביבות ממתינות".
לחיצה על שורה פותחת את הקריאה הרלוונטית.

### לשונית 2: "מטריצה"

עובדים מול מערכות, ובתא הסביבות הפעילות. אפשר להפוך צירים (מערכות מול עובדים)
ולמיין לפי כל עמודה. סינון לפי מחלקה, מערכת, סביבה וסטטוס. זו "תמונת המצב"
לביקורת: מי נגיש למה, עכשיו. טבלה סמנטית עם כותרות עמודה ופקדים מזוהים (כלל
הנגישות של רשימות הנכסים).

### לשונית 3: "פרוטוקולים"

- **לפי עובד:** ציר זמן של כל ההרשאות של העובד, קישורים לקריאות, הפרוטוקולים
  השמורים, ו"הפק פרוטוקול מצב עדכני".
- **לפי מערכת:** בוחרים מערכת (ואופציונלית סביבה) ומפיקים "כל מי שנגיש לפריוריטי־כספים",
  עם תאריכי תוקף, ביצוע וניתוק. מתאים לסקר הרשאות תקופתי.

### לשונית 4: "מערכות וסביבות" (הגדרות)

ניהול רשימת המערכות: שם, שיטת פתיחה, אחראי וסדר. מתחת לכל מערכת, סביבות בשדות
חופשיים: הוספה, שינוי שם והשבתה. אין מחיקה של סביבה שיש לה הרשאות. רק משביתים.

### בקשה יזומה (לא דרך קליטה)

כפתור "בקשת הרשאה" / "בקשת ניתוק" לעובד קיים, למשל כשעובד עובר מחלקה: אותו
טופס בחירת מערכות וסביבות ואותה חתימה. נוצרות קריאה לכל אחראי ופרוטוקול אחיד.

## 9. החיבור לטופס קליטת עובד

בתוך `NewOnboardingDialog` מתווסף שלב/מקטע **"הרשאות למערכות"**, נפרד מהמשאבים:

1. רשימת מערכות עם תיבות סימון.
2. סימון מערכת פותח בחירת סביבות (בחירה מרובה, עם אפשרות "+ סביבה חדשה" למי
   שמורשה).
3. שדה "בתוקף מ" מתמלא ב-`start_date` 08:00 וניתן לשינוי לכל מערכת.
4. "העתק מעובד קיים" מעתיק גם הרשאות (כמו `copyFromEmployee` הקיים לנכסים).
5. ב"שליחה לתפעול" (`SendToOpsDialog`) משאבי אנוש חותמת (`SignaturePad`), ו-
   `request_access` מפיקה יחד את הקריאות לכל אחראי ואת הפרוטוקול האחיד. הקריאות
   האלה נפרדות מקריאת הקליטה של הציוד, כי מבצעים אחרים מטפלים בהן.

## 10. סיום העסקה

כשמתחיל תהליך ניתוק (הפונקציה האטומית הקיימת), נוצרת אוטומטית הגשת ניתוק עם כל
ההרשאות הפעילות של העובד: **קריאת "ניתוק הרשאות" לכל אחראי** (כוננים לאיש ה-IT)
ו**פרוטוקול ניתוק אחיד**. מועד הניתוק המבוקש הוא יום העבודה האחרון, וניתן לשינוי.
ביצוע כל שורה ממלא `revoked_at`, וכך הפרוטוקול מציג תקופה מלאה "מ… עד…" לכל הרשאה.
פרוטוקול הניתוק נשמר בתיק העובד לצד טופס הניתוק.

## 11. מיגרציה מהמצב הקיים

סקריפט חד-פעמי שממיר את הפריטים בדומיין `digital` שמשויכים לעובדים לשורות
`access_grants` בסטטוס `active`. `effective_from` נלקח מתאריך השיוך, ואם אין, מ-
`start_date` 08:00, עם הערה "יובא מהמשאבים". אחרי האימות מסתירים את ההרשאות ממסך
המשאבים.

## 12. שלבי ביצוע מוצעים

1. טבלאות, RLS, פונקציות DB, יומן ביקורת ולשונית "מערכות וסביבות".
2. `request_access`: קריאה מסוג `access` לכל אחראי, פאנל הביצוע בתוך הקריאה, ופרוטוקול אחיד לעובד.
3. מסך `/system-access`: קריאות פתוחות, מטריצה ופרוטוקולים, בתצוגה לפי עובד ולפי מערכת.
4. חיבור לטופס הקליטה וחתימת משאבי אנוש.
5. אוטומציות: תפעול 360 (`manage-users`), מסימון (אחרי אימות API).
6. קריאת ניתוק מתוך תהליך הניתוק, ומיגרציה מהמשאבים.

## 13. שאלות פתוחות

1. **מסימון:** ל-`create-mesimon-task` יש היום רק יצירת משימות ושליפת משתמשים. צריך
   לאמת שב-API של מסימון יש endpoint ליצירת משתמש, ומה הוא מקבל (מייל, הרשאות,
   סביבה?).
2. **אחראים:** מי האחראי של כל מערכת (תפקיד או אדם מסוים)? האם המבקש/ת יכול/ה לסמן
   ביצוע בעצמו/ה? ההמלצה: לא, הפרדת סמכויות.
3. **הפרוטוקול האחיד בקריאה של איש ה-IT:** הוא כולל את כל המערכות של העובד. אם איש
   ה-IT לא אמור לראות אותן, מציגים לו בקריאה גרסה מסוננת רק עם הכוננים, והאחיד
   נשמר בתיק העובד.
4. **סביבות בתפעול 360:** האם "סביבה" כאן היא תפקיד (`user_roles`)? אם כן, אישור
   יכול לתת גם את התפקיד, דרך `set-role` הקיים, שכבר כותב ל-`permission_audit_log`.
5. **כוננים:** האם הסביבות הן אותיות כוננים / תיקיות, ונדרשת גם רמת הרשאה
   (קריאה / כתיבה)? אם כן, מוסיפים שדה "רמה" להרשאה.
6. **שעת ברירת מחדל 08:00:** קבועה לכל החברות, או הגדרה ברמת חברה?
