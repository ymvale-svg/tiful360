# תוכנית מימוש: שרשרת הרשאות מקליטת עובד ועד ביצוע

משלים את האפיון ב-`org-system-access.md`, ומחליף את סעיף 3 שם (מי פותח את הקריאות).
סטטוס: תוכנית לאישור · אין עדיין קוד.

## 0. ההחלטה המרכזית: לנתק את ההרשאות מהמשאבים

**ההמלצה: לנתק.** הרשאות עוברות לקטלוג ולטבלאות משלהן, והמשאבים נשארים לציוד,
רישיונות ומנויים.

מה קיים היום: הרשאה היא קטגוריה בדומיין `digital` של המשאבים (`assetDomains.ts`,
"גישות דיגיטליות"). קבוצות המשנה (`asset_groups`) משמשות כמעין סביבות, ובקליטה היא
נשמרת כ-`onboarding_items` מסוג `access` (`NewOnboardingDialog.tsx`).

למה זה לא מחזיק:

| צורך | מה המשאבים נותנים |
|---|---|
| כונן P ← תיקיות A, B, C, D | שתי רמות בלבד, קטגוריה וקבוצה, בלי היררכיה |
| מאיזה יום ושעה ההרשאה בתוקף | אין. רק שדות של חשבון (שם משתמש, MFA, תפוגת סיסמה) |
| מבוקש ← נשלח לאחראי ← בוצע ← נותק | אין מחזור חיים. רק `in_use` / `in_stock` של נכס |
| עובד × מערכת × סביבה, בלי לייצר "נכס" לכל הרשאה | כל שיוך הוא רשומת `assets` |

סנכרון דו-כיווני בין שני מודלים כאלה שביר. לכן יהיה מקור אמת אחד, `access_grants`,
וכל המסכים יקראו ממנו: הקליטה, מסך ההרשאות, הקריאות ותיק העובד.

מה קורה במשאבים: בלשונית "גישות דיגיטליות" יופיע באנר "הרשאות מנוהלות במסך הרשאות
מערכות", עם קישור. הקטגוריות הקיימות יומרו לקטלוג החדש (שלב 6), והשיוכים
הקיימים יומרו להרשאות פעילות. רישיונות תוכנה ומנויים (דומיין `licenses`) נשארים
במשאבים, כי הם עלות וכמות מושבים, לא גישה.

## 1. השרשרת

```
 ① משאבי אנוש: טופס קליטה
    בוחרת מערכת ← סביבות/תיקיות ← "בתוקף מ" (יום ראשון 08:00) ← חותמת ושולחת
          │
          ▼
 ② אליך: "בקשת הרשאות – אחמד פוקרה"  (קריאת אם, ותור במסך ההרשאות)
    לכל שורה אתה בוחר:
      • בצע בעצמי      (פריוריטי / ויפלנס / סמנטו: פותח וסומן "בוצע")
      • בצע אוטומטית   (תפעול 360, מסימון)
      • שלח לאחראי     (כונן P → איש IT)
          │
          ▼
 ③ איש ה-IT: קריאה חדשה (קריאת בת)
    "לפתוח לאחמד פוקרה בכונן P את התיקיות A, B, C, D"
    + קישור לפרוטוקול הבקשה החתום
    הוא פותח, מסמן שורות "בוצע" (או סוגר את הקריאה = הכול בוצע)
          │
          ▼
 ④ חוזר אליך אוטומטית:
    • השורות הופכות ל"פעיל" עם מי ומתי
    • בקריאת האם נרשמת תגובה: "כונן P – A, B, C, D נפתח ע"י אחמד IT, 09/11 10:42"
    • מייל/התראה אליך
    • כשכל השורות של העובד טופלו: קריאת האם נסגרת, נוצר פרוטוקול ביצוע אחיד,
      והסעיף "הרשאות" בצ'קליסט הקליטה מסומן כהושלם
```

ניתוק עובד עובר בדיוק את אותה שרשרת, ונפתחת אוטומטית מתהליך הניתוק במקום מטופס
הקליטה.

## 2. הקטלוג: מערכות, סביבות ותיקיות

קטלוג אחד בלשונית "מערכות וסביבות" במסך ההרשאות:

```
פריוריטי          (אחראי: אתה)
  ├─ כספים
  ├─ הנדסה
  ├─ רכש
  └─ התחדשות עירונית
ויפלנס / סמנטו    (אחראי: אתה)
תפעול 360         (אוטומטי)
מסימון            (אוטומטי)
כוננים            (אחראי: איש IT)
  ├─ כונן P
  │    ├─ A
  │    ├─ B
  │    ├─ C
  │    └─ D
  └─ כונן S
       └─ ...
```

- סביבה יכולה להכיל סביבות משנה (`parent_id`), וכך כונן ← תיקיות. בפריוריטי
  יש רמה אחת.
- הכול בשדות חופשיים: הוספה, שינוי שם והשבתה. אין מחיקה של פריט שיש לו הרשאות.
- לכל מערכת יש **אחראי ברירת מחדל**, שמוצע אוטומטית בשלב ②. אתה יכול לשנות.

שינוי לטבלה מהאפיון:

```sql
alter table org_system_environments
  add column parent_id uuid references org_system_environments(id);  -- כונן ← תיקייה
```

## 3. שלב ①: טופס הקליטה (`NewOnboardingDialog`)

היום ההרשאות נבחרות שם מתוך קטגוריות המשאבים. במקומן נוסיף מקטע **"הרשאות
למערכות"**, רכיב חדש בשם `AccessPicker` שקורא מהקטלוג:

```
☑ פריוריטי         בתוקף מ: [02/11/2026] [08:00]
    ☑ כספים  ☐ הנדסה  ☑ רכש  ☐ התחדשות עירונית
☑ כוננים           בתוקף מ: [02/11/2026] [08:00]
    כונן P:  ☑ A  ☑ B  ☑ C  ☑ D   (☑ כל הכונן)
    כונן S:  ☐ ...
☐ ויפלנס
☑ תפעול 360
```

- "בתוקף מ" מתמלא מ-`start_date` של העובד בשעה 08:00, וניתן לשינוי לכל מערכת.
- "העתק מעובד קיים" מעתיק גם את ההרשאות הפעילות שלו.
- במצב עריכה (`saveEdit`) חלים אותם כללים כמו היום: שורה שכבר בוצעה לא נמחקת.
- בשליחה (`SendToOpsDialog`, שכבר אוסף חתימה) נקראת פונקציית DB אחת,
  `request_access`, שיוצרת בטרנזקציה אחת את ההגשה, את שורות `access_grants` בסטטוס
  `requested` ואת קריאת האם אליך. ההרשאות לא נכתבות יותר ל-`onboarding_items`.

## 4. שלב ②: אצלך, בקריאת האם ובמסך ההרשאות

קריאת האם היא `it_tickets` מסוג חדש `access`, שמוקצית אליך, עם הכותרת "בקשת
הרשאות – אחמד פוקרה". אותו תוכן מופיע במסך ההרשאות בלשונית "בקשות לטיפול".
בכניסה מופיעים פרוטוקול הבקשה החתום ורשימת שורות ממוינת לפי מערכת:

| ☐ | מערכת | סביבה / תיקיות | בתוקף מ | אחראי מוצע | סטטוס |
|---|---|---|---|---|---|
| ☐ | פריוריטי | כספים, רכש | 02/11 08:00 | אתה | ממתין |
| ☐ | תפעול 360 | — | 02/11 08:00 | אוטומטי | ממתין |
| ☐ | כוננים | כונן P: A, B, C, D | 02/11 08:00 | איש IT | ממתין |

פעולות על שורות מסומנות:

- **"בצע"**: בשורה אוטומטית נפתח משתמש מיד. בשורה ידנית נפתח דיאלוג עם תאריך,
  שעת ביצוע ושם משתמש.
- **"שלח לאחראי"**: כל השורות המסומנות שמיועדות לאותו אדם הופכות **לקריאת בת אחת**
  אליו. הטקסט נבנה אוטומטית ("לפתוח לאחמד פוקרה בכונן P את התיקיות A, B, C, D")
  וניתן לעריכה לפני השליחה.
- **"דחה"**, עם סיבה.

אפשר להגדיר בהמשך, לכל מערכת, "שלח אוטומטית לאחראי בלי לעבור דרכי". ברירת המחדל
היא שהכול עובר דרכך, כפי שביקשת.

## 5. שלב ③: קריאת הבת לאיש ה-IT

- `it_tickets` מסוג `access`, עם הקצאה לאיש ה-IT וקישור לקריאת האם (עמודה חדשה
  `parent_ticket_id`). המייל יוצא דרך `notify-it-ticket` הקיים.
- **זו קריאה נפרדת, לא "העברה ל-IT".** ה-`it_forwards` הקיים רק שולח מייל על אותה
  קריאה, ואיש ה-IT לא יכול לסגור אותה. כאן הוא מקבל קריאה משלו וסוגר אותה.
- בקריאה הוא רואה רק את השורות שנשלחו אליו, וקישור לפרוטוקול הבקשה. הפרוטוקול
  מסונן לשורות שלו (ראו החלטה 3).
- הוא יכול לסמן כל תיקייה "בוצע", או ללחוץ "סגור קריאה", שמסמן את כל מה שנותר
  כבוצע עם זמן הסגירה.
- אם משהו לא נפתח, הוא מסמן "לא בוצע" עם הסבר, והשורה חוזרת אליך כ"הוחזר".

## 6. שלב ④: החזרה אליך והסנכרון

סגירת קריאת הבת קוראת לפונקציית DB אחת, `complete_access_dispatch`, שבטרנזקציה
אחת:

1. מעדכנת את השורות ל-`active`, כולל `executed_at`, `executed_by` וצילום שם.
2. מוסיפה תגובה בקריאת האם: "נפתח ע"י …".
3. סוגרת את קריאת האם אם לא נשארו שורות פתוחות. העדכון מותנה, כמו
   ב-`ticket-handling-status`.

אחרי הטרנזקציה נשלח מייל אליך. אם זו הייתה השורה האחרונה, מופק פרוטוקול הביצוע
האחיד ונשמר בתיק העובד.

### איפה כל סטטוס מופיע

| מסך | מה רואים | מקור |
|---|---|---|
| קליטת עובד (`OnboardingChecklist`) | מקטע "הרשאות" עם השורות והסטטוס שלהן, וקישור לקריאות. הקליטה נחשבת הושלמה רק כשכל השורות טופלו | `access_grants` לפי `onboarding_process_id` |
| מסך הרשאות | בקשות לטיפול, מטריצה ופרוטוקולים, לפי עובד או לפי מערכת | `access_grants` |
| קריאות שירות | קריאת אם אצלך, קריאות בת אצל האחראים | `it_tickets` + קישור |
| תיק עובד | פרוטוקולי בקשה, ביצוע וניתוק | `employee_documents` |
| משאבים | באנר וקישור בלבד | — |

הכול קורא מאותן שורות, ולכן אין מה "לסנכרן". אין העתקים.

## 7. שינויי מבנה נתונים ביחס לאפיון

- `access_tickets` מקבלת `role` (`hub` לקריאת האם, `dispatch` לקריאת בת) ו-`parent_id`.
- `access_grants` מקבלת `hub_ticket_id` ו-`dispatch_ticket_id`, וסטטוסים:
  `requested` → `dispatched` → `active` / `returned` / `rejected` → `revoke_requested`
  → `revoke_dispatched` → `revoked`.
- `it_tickets` מקבלת `parent_ticket_id`, והערך `access` נוסף ל-`ticket_type`.
- `org_system_environments` מקבלת `parent_id` (סעיף 2).
- כל הכתיבות עוברות בפונקציות DB: `request_access`, `dispatch_access`,
  `complete_access_grant`, `complete_access_dispatch`, `return_access_grant`,
  `request_revocation`. הן בודקות tenant ותפקיד, ורושמות מבצע וצילום שם. יומן
  הביקורת נשמר ב-`permission_audit_log` דרך triggers.

עובדת מקצה לקצה.

## 9. החלטות שנדרשות ממך

1. **לנתק מהמשאבים?** ההמלצה: כן (סעיף 0).
2. **הכול עובר דרכך, או שליחה אוטומטית לאחראי?** ההנחה כרגע: הכול עובר דרכך, ואפשר
   לסמן מערכת מסוימת כ"ישירות לאחראי".
3. **מה איש ה-IT רואה:** את הפרוטוקול המלא של העובד, או רק את השורות שלו? ההמלצה:
   רק את שלו. הפרוטוקול המלא נשמר בתיק העובד.
4. **תיקיות:** האם צריך גם רמת הרשאה, קריאה בלבד או קריאה וכתיבה?
5. **מסימון:** האם ל-API שלהם יש פעולה ליצירת משתמש.
