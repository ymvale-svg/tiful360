## 2. ההחלטה הראשונה: למי שייך פרויקט ה-Supabase?

זו השאלה שקובעת את היקף העבודה. **לבדוק:** להיכנס ל-supabase.com עם החשבון שלכם ולחפש את הפרויקט `rhzmhiknbcipucfvgkok`.

| מצב | משמעות | היקף |
|---|---|---|
| **א. הפרויקט בחשבון שלכם** | ה-backend נשאר כמו שהוא. מחליפים רק את שירותי Lovable שמעליו | 2–3 שבועות, בלי העברת נתונים ובלי לגעת בסוכני הנוכחות |
| **ב. Lovable Cloud** (הסבירות הגבוהה, לפי `LOVABLE_DB_MIGRATION_URL` ו-`cloud-auth-js`) | צריך פרויקט Supabase חדש בחשבון שלכם והעברה של סכמה, נתונים, משתמשים, קבצים ו-secrets | 4–6 שבועות, כולל חלון מעבר |

**למה Render + Supabase ולא Render בלבד:** Render מצוין לאירוח האתר ולשירותים, אבל אין לו מקבילה ל-Supabase Auth, Storage, RLS ו-Edge Functions. מעבר מלא ל-Render Postgres פירושו לכתוב מחדש את ההתחברות, את הרשאות ה-RLS (31 מיגרציות), את אחסון הקבצים ו-35 פונקציות. זה סיכון גבוה מאוד לעבודה השוטפת, ולכן **לא מומלץ**. ההמלצה: **Render לאתר (ובעתיד גם לשירותים), Supabase בחשבון שלכם ל-backend.**

## 4. שלבי העבודה

כל שלב נכנס כ-PR נפרד, נבדק ונפרס **לפני** שמנתקים את מה ש-Lovable מספק. שלבים 1–6 לא משנים את מה שהמשתמשים רואים.

### שלב 0 – הכנות וגיבוי (יום 1–2) · ללא השפעה
1. **גיבוי מלא** לפני כל שינוי: `pg_dump` של המסד (סכמה + נתונים + `auth`), רשימת buckets וקבצים, ורשימת ה-secrets של ה-Edge Functions (שמות בלבד: `LOVABLE_API_KEY`, `RESEND_API_KEY`, `MESIMON_*`, `ATTENDANCE_INGEST_TOKEN`, `INGEST_TOKEN`, `GIT_API_*`, `APP_SITE_URL`, `ATTENDANCE_HARD_MIN_DATE`).
2. לבדוק את סעיף 2 (בעלות על הפרויקט).
3. במצב ב': לבקש מ-Lovable גישת חיבור ישירה למסד, או ייצוא מלא שכולל את `auth.users` עם ה-hash של הסיסמאות ואת הקבצים ב-Storage. **בלי זה אי אפשר להעביר משתמשים בלי לאפס סיסמאות.** זו נקודת הסיכון הגבוהה ביותר, ולכן מתחילים בה.
4. לפתוח חשבונות: Render, Resend (או לוודא שהקיים פעיל, הוא כבר בשימוש ב-`send-tax101-*`), Google Cloud (OAuth client), ומפתח AI.
5. לוודא שה-DNS של `tiful360.com` ושל `notify.tiful360.com` בשליטתכם ולא אצל Lovable.

### שלב 3 – AI ישיר (יום 5–7) · ללא השפעה למשתמש · L6
- ליצור `_shared/ai.ts` עם פונקציה אחת `chatCompletion({ messages, tools, model, signal })`. שלוש הפונקציות קוראות רק לה, במקום לבנות `fetch` ל-gateway כל אחת בעצמה.
- **ספק מומלץ להתחלה:** Gemini API ישירות דרך ה-endpoint התואם-OpenAI של Google. זה אותו מודל (`gemini-2.5-flash`) ואותו פורמט הודעות, כך שהתנהגות זיהוי התלושים והפוליסות לא משתנה. החלפה לספק אחר (למשל Claude) תהיה שינוי בקובץ אחד.
- secrets חדשים: `AI_API_KEY`, `AI_BASE_URL`, `AI_MODEL` (במקום `LOVABLE_API_KEY` ו-`LOVABLE_AI_MODEL`).
- **אימות:** להריץ את `split-payslips` על קובץ תלושים קיים ולהשוות שיוך לעובדים מול התוצאה הקודמת. להריץ `extract-insurance-policy` על פוליסה קיימת. לשאול את העוזר 5 שאלות קבועות.
- בדיקות יחידה ל-`_shared/ai.ts` עם `fetch` מדומה: כותרות, timeout ושגיאה 429.

### שלב 4 – מיילים דרך Resend (יום 7–10) · ללא השפעה · L7
- **DNS:** לאמת את `notify.tiful360.com` ב-Resend (SPF, DKIM, DMARC). **לא למחוק** את רשומות ה-DNS של Lovable עד סוף שלב 8.
- `_shared/send-email-logged.ts`: להחליף את `sendLovableEmail` ב-`sendViaResend()`. שאר הקובץ (`EmailLayout`, `formatEmailHtml`, `resolveEmailBrand` ו-`email_send_log`) נשאר, לפי חוק המיילים ב-`AGENTS.md`. לאחד את `send-tax101-email` ואת `send-tax101-invite`, שכבר קוראות ל-Resend ישירות, לאותו helper.
- `auth-email-hook`: לעבור לחתימת ה-Send Email Hook של Supabase (standard webhooks, `SEND_EMAIL_HOOK_SECRET`) במקום `lovable-signature`, ולשלוח דרך אותו helper. התבניות ב-`_shared/email-templates/` לא משתנות.
- `handle-email-events`: להחליף ב-webhook של Resend (`email.delivered`, `email.bounced`, `email.complained`) שמעדכן את אותה טבלת לוג.
- **הפעלה מדורגת:** משתנה `EMAIL_PROVIDER=lovable|resend`. מתחילים ב-`resend` רק ל-`preview-transactional-email` ולמייל בדיקה לכתובת פנימית, ואחרי יום תקין עוברים לכל המיילים.
- **אימות:** איפוס סיסמה, הזמנת משתמש, מייל קריאת שירות ותזכורת תפוגה מגיעים ל-Gmail ול-Outlook, לא לספאם, ובמיתוג של החברה הנכונה.

### שלב 5 – כניסה עם Google בלי Lovable (יום 10–12) · L5
- Google Cloud Console: OAuth Client מסוג Web, עם redirect URI `https://<project>.supabase.co/auth/v1/callback`. ב-Supabase → Auth → Providers → Google: להזין את ה-Client ID וה-Secret.

- לשמור על חוק ה-OAuth return path: `redirectTo` עובר דרך המאמת הקנוני ב-`oauth-return-path.ts`, וה-`next` נצרך אחרי ההתחברות. לעדכן את החוק ב-`AGENTS.md`, כי "managed social login" כבר לא רלוונטי.
- להחליף את `previewAuthStorage` ב-`localStorage` רגיל ולמחוק את הקובץ (L4).
- **אימות:** כניסה עם Google, משתמש קיים מקבל את אותו `user_id` (Supabase מקשר לפי מייל מאומת). לבדוק גם חזרה ל-`next` וגם כניסה מאפליקציית ה-Android.
- בדיקות: להרחיב את `oauth-return-path` ולהוסיף בדיקה ל-`googleSignIn` (redirect מאומת, ללא open redirect).

### שלב 6 – MCP, telemetry, מיתוג וכתובות (יום 12–15) · L8, L9, L11, L12
- **MCP:** להוציא את `supabase/functions/mcp` מהיצירה האוטומטית. לפי ההוראה בראש הקובץ: מוחקים את שורת ה-banner, ואחר כך מחליפים את `@lovable.dev/mcp-js` ב-`@modelcontextprotocol/sdk` הרשמי (היום הוא מגיע רק כתלות עקיפה, וצריך להוסיף אותו ישירות). שלושת הכלים הקיימים נשארים זהים: read-only, client לפי המשתמש הקורא ובדיקת access-block, לפי חוק ה-MCP. את ה-OAuth לסוכנים מעבירים ל-OAuth Server של Supabase Auth, ומעבירים את מסך האישור מ-`/.lovable/oauth/consent` ל-`/oauth/consent`, עם redirect מהכתובת הישנה.
  - *חלופה בסיכון נמוך:* אם אף סוכן חיצוני לא מחובר היום, לכבות את ה-MCP זמנית ולהחזיר אותו אחרי המעבר.
- **Telemetry:** להחליף את `__lovableEvents` ב-no-op (או בכלי משלכם), בלי לשנות את הקריאות ב-UI (חוק ה-fail-open).
- **כתובות:** להחליף כל fallback ל-`*.lovable.app` ב-`Deno.env.get("APP_SITE_URL") ?? "https://tiful360.com"`, ולאחד את `APP_ORIGIN` הקשיח (`signLink.ts`, `send-handover-sign-link`, `create-mesimon-task`, `notify-onboarding-process`) לקבוע אחד.
- **מיתוג:** `index.html` (author, twitter) ו-"Lovable AI" ב-`AiAssistantWidget`.
- `drizzle.config.ts`: `LOVABLE_DB_MIGRATION_URL` → `DATABASE_URL`.
- בדיקת ארכיטקטורה `noLovable.test.ts`: אין `lovable` בקוד המקור (מלבד ה-redirect הישן ותיעוד).

### שלב 7 – העברת ה-backend (רק במצב ב', שבוע 4–5)
מדלגים על השלב הזה אם הפרויקט כבר בחשבון שלכם.

**הכנה (ללא השפעה):**
1. ליצור פרויקט Supabase חדש **באותו אזור** ובתוכנית בתשלום (נדרשת ל-pg_cron, ל-PITR ולגיבויים).
2. להחיל את 160 המיגרציות (`supabase db push`), ולוודא שהסכמה זהה למקור (`supabase db diff`).
3. לתקן את 5 המיגרציות שבהן כתובת הפרויקט קשיחה: מיגרציה חדשה שקוראת את הכתובת מה-vault (`project_url`) ומתזמנת מחדש את ה-cron jobs.
4. לפרוס את כל 35 הפונקציות עם `verify_jwt` מ-`config.toml`, ולהגדיר secrets. לשמור את ערכי `ATTENDANCE_INGEST_TOKEN`/`INGEST_TOKEN` כדי שסוכנים שכבר מוגדרים יעבדו מול הפרויקט החדש בלי שינוי טוקן.
5. Storage: ליצור buckets עם אותן מדיניות. סקריפט העתקה (`scripts/migrate-storage.ts`) מעתיק כל קובץ ומשווה גודל ו-checksum. נתיבי הקבצים זהים (company-scoped), ולכן ה-DB לא משתנה.
6. **חזרה גנרלית** על עותק: שחזור הנתונים לפרויקט החדש, הפניית `tiful360.onrender.com` אליו, ובדיקת כל התהליכים העסקיים (רשימת בדיקה בסעיף 6).

**חלון המעבר (מוצאי שבת, כ-3 שעות):**
1. הודעה מראש למשתמשים, ובאנר "תחזוקה" באתר הישן.
2. הקפאת כתיבה: מצב read-only באפליקציה ועצירת ה-cron jobs בישן.
3. `pg_dump` של `public`, `auth` (כולל hash של סיסמאות ו-identities) ו-`storage.objects`, ושחזור לחדש. השלמת הקבצים שהשתנו מאז ההעתקה הראשונה.
4. בדיקת ספירות: מספר שורות בכל טבלה, מספר משתמשים, מספר קבצים.
5. מעבר ב-Render ל-`VITE_SUPABASE_URL` של הפרויקט החדש ופריסה מחדש.
6. **כל המשתמשים יתנתקו פעם אחת** (סוד JWT אחר). הסיסמאות נשמרות.

**מערכות חיצוניות (באותו ערב):**
- **סוכני נוכחות:** לעדכן את `INGEST_URL` בכל מחשב. החתמות לא יאבדו בזמן הניתוק: `agent-py` מקדם את `last_punch_at` רק אחרי שליחה מוצלחת (`main.py:100-104`), וקורא מחדש מהשעון את כל מה שאחריו. הכתובת כבר נקראת מ-`.env` (`INGEST_URL`), ולכן העדכון הוא שינוי שורה אחת והפעלה מחדש של השירות. כדאי להכין סקריפט אחד לכל המחשבים ולוודא שזיכרון השעון מחזיק את ההחתמות של חלון המעבר.
- **Mesimon:** לעדכן את כתובת ה-callback ל-`it-api`.
- **קישורי `leave-ics`:** בפרויקט הישן (כל עוד הוא קיים) להשאיר פונקציה שמחזירה redirect 301 לכתובת החדשה, ולשלוח לעובדים קישור חדש.

**חזרה אחורה:** עד שמבטלים את הפרויקט הישן, חזרה היא החזרת `VITE_SUPABASE_URL` ב-Render ופריסה מחדש (כ-5 דקות). נתונים שנכתבו בחדש בזמן הזה יועתקו ידנית.

### שלב 8 – מעבר דומיין וניתוק סופי (שבוע 5–6)
1. להוריד את ה-TTL של רשומות ה-DNS ל-5 דקות, יומיים לפני.
2. להפנות את `tiful360.com` ל-Render (Custom Domain + SSL). לבדוק `assetlinks.json` ואת אפליקציית ה-Android.
3. לעקוב שבוע: שגיאות ב-Edge Functions, מיילים שנכשלו ב-`email_send_log`, והחתמות נוכחות.
4. **ניתוק:**
   - ב-Lovable: לנתק את סנכרון GitHub ולמחוק את ענף `lovable-sync`.
   - להסיר את הדומיין מ-Lovable.
   - להסיר את `@lovable.dev/cloud-auth-js` ואת `@lovable.dev/mcp-js` מ-`package.json`.
   - למחוק את `src/integrations/lovable/`, `previewAuthStorage.ts` ו-`.lovable/` (אחרי העברת `north-star.md` ל-`docs/`).
   - למחוק את רשומות ה-DNS של שליחת המיילים של Lovable.
   - לבטל את `LOVABLE_API_KEY`.
5. במצב ב': להשאיר את הפרויקט הישן במצב read-only 30 יום, לקחת גיבוי סופי ורק אז לבטל.
6. לעדכן את `AGENTS.md`: Render + Supabase, חוק OAuth מעודכן, והחלפת `__lovableEvents`.
